    12. Version 7 - PAM multi-view / multi-page web application

    Here we return to the initial architecture where the [métier] layer was simulated. We now know that this can be easily replaced by the actual [métier] layer. The simulated [métier] layer facilitates testing.

    A JSF application is of the MVC type (Model-View-Controller):

    1. the [Faces Servlet] servlet is the generic controller provided by JSF. This controller is extended by application-specific event handlers. The event handlers encountered so far were methods of the classes serving as templates for the JSF pages
    2. The JSF pages send responses to the client browser. These are the application views.
    3. The JSF pages contain dynamic elements known as the page template. Note that for some authors, the model encompasses the entities manipulated by the application, such as the FeuilleSalaire or Employee classes. To distinguish between these two models, we can refer to the application model and the JSF page model.

    In the JSF architecture, navigating from a JSFi page to a JSFj page can be problematic.

    1. The JSFi page has been displayed. From this page, the user triggers a POST via some event [1]
    2. in JSF, this POST will generally be handled by a C method of the Mi model of the page JSFi. We can say that the C method is a secondary controller.
    3. If, at the end of this method, the page JSFj needs to be displayed, controller C must:
    • update [2c], the Mj template of page JSFj
    • return [2a] to the main controller, the key for navigation that will enable the display of page JSFj

    Step 1 requires that the Mi template for page JSFi reference the Mj template for page JSFj. This complicates matters somewhat, making the Mi templates dependent on one another. Indeed, the C manager for the Mi template that updates the Mj template must be aware of the latter. If the Mj template needs to be changed, the C handler for the Mi template will also need to be changed.

    There is one case where model dependencies can be avoided: when there is a single M model used by all JSF pages. This architecture is only usable in applications with just a few views, but it is very simple to use. This is the one we are currently using.

    12.2.4. The [métier] layer

    The simulated [métier] layer is modified as follows:

    
package metier;
 
...
public class Metier implements ImetierLocal, Serializable {
 
  // list of employees
  private Map<String,Employe> hashEmployes=new HashMap<String,Employe>();
  private List<Employe> listEmployes;
 
  // get your payslip
  public FeuilleSalaire calculerFeuilleSalaire(String SS,
    double nbHeuresTravaillées, int nbJoursTravaillés) {
    // we get the employee
    Employe e=hashEmployes.get(SS);
    // an exception is thrown if the employee does not exist
    if(e==null){
      throw new PamException(String.format("L'employé de n° SS [%s] n'existe pas",SS),1);
    }
    // a fictitious payslip is returned
    return new FeuilleSalaire(e,new Cotisation(3.49,6.15,9.39,7.88),e.getIndemnite(),new ElementsSalaire(100,100,100,100,100));
  }
 
  // list of employees
  public List<Employe> findAllEmployes() {
    if(listEmployes==null){
      // create a list of three employees
      listEmployes=new ArrayList<Employe>();
      listEmployes.add(new Employe("254104940426058","Jouveinal","Marie","5 rue des oiseaux","St Corentin","49203",new Indemnite(2,2.1,2.1,3.1,15)));
      listEmployes.add(new Employe("260124402111742","Laverti","Justine","La brûlerie","St Marcel","49014",new Indemnite(1,1.93,2,3,12)));
      // employee dictionary
      for(Employe e:listEmployes){
        hashEmployes.put(e.getSS(),e);
      }
      // we add an employee who doesn't exist in the dictionary
      listEmployes.add(new Employe("X","Y","Z","La brûlerie","St Marcel","49014",new Indemnite(1,1.93,2,3,12)));
    }
    // we return the list of employees
    return listEmployes;
  }
}
    1. line 8: the list of employees
    2. Line 7: The same list in the form of a dictionary indexed by the employee ID SS
    3. Lines 24–39: The findAllEmployes method, which returns the list of employees. This method creates a hard-coded list and references it via the employees field in line 8.
    4. Lines 27–33: A list and a dictionary of two employees are created
    5. Line 35: An employee is added to the employees list (line 8) but not to the hashEmployes dictionary (line 7). This is done so that the employee appears in the employee combo box but is not recognized by the calculerFeuilleSalaire method (line 14), causing it to throw an exception (line 17).
    6. lines 11–21: the calculerFeuilleSalaire method
    7. line 14: the employee is searched for in the dictionary hashEmployes using their ID SS. If not found, an exception is thrown (lines 16–18). Thus, we will have an exception for the employee with ID SS X added on line 35 to the employee list but not to the hashEmployes dictionary.
    8. On line 20, a dummy pay slip is created and returned.
